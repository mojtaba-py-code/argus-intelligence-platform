# Phase 20 - Observability

## 1. Purpose
When something is slow, failing or expensive, an operator must be able to answer *where* and
*why* without guessing - and the telemetry that answers it must not become a new place where
customer data leaks. This phase adds distributed tracing across processes, completes the
metrics (every process scrapeable, no metric defined but never recorded), and ships alert
rules with runbooks, a dashboard and a local observability stack.

## 2. Architecture
```
api      TracingMiddleware ─ server span "POST /api/v1/orgs/{org_id}/projects/{project_id}/research-jobs"
           └─ JobQueue.enqueue: jobs.trace_parent = traceparent of the current span
worker   span "job research.run" (CONSUMER, parent = jobs.trace_parent)
           └─ "research.stage plan|collect|analyze|verify|contradictions|report"
                └─ "agent.run planner|analyst|..." ─ "chat <model>" (gen_ai.* tokens, cost, outcome)
                                                   └─ "agent.tool <declared name>" (outcome)
                └─ "knowledge.retrieve" · "egress.fetch" (server.address only) · "db SELECT|..."
scheduler span "scheduler <task>"

spans ─ BatchSpanProcessor ─ OTLP/HTTP ─► collector (memory limiter, attribute scrub, batch)
                                             ─► trace store (Jaeger locally)
metrics: api /metrics · worker and scheduler /metrics on ARGUS_OBSERVABILITY__METRICS_PORT
         ─► Prometheus (alert rules) ─► Grafana (generated dashboard)
logs:    structlog JSON, redacted, + trace_id / span_id of the active span
```

## 3. Why this design
* **Own instrumentation instead of auto-instrumentation.** The usual HTTP-client
  instrumentations inject `traceparent` into every outgoing request - here that includes fetches
  of arbitrary websites chosen by search results, which would hand internal ids to third parties.
  Server, job, stage, agent, model, tool, retrieval, egress and database spans are created by
  ~200 lines of explicit code with an allow-list of attributes, and the unused auto-instrumentation
  packages were not needed.
* **FastAPI's native telemetry is switched off.** FastAPI 0.142 ships OpenTelemetry support that
  continues any incoming `traceparent`, can export request-validation errors *with the submitted
  values* (passwords included) and stack traces as log records, and configures exporters from
  `OTEL_*` environment variables. Each of those contradicts a rule of this platform, so
  `create_app` disables it and the Argus middleware does the job.
* **Trace context crosses the queue in a column, not in the payload.** `jobs.trace_parent` is a
  separate column with a CHECK constraint that accepts a W3C `traceparent` and nothing else:
  task payloads stay strictly validated and the column cannot carry arbitrary data.
* **Incoming trace context is not trusted by default.** A client choosing our trace ids could
  splice itself into other traces; behind a gateway that sets the header itself,
  `ARGUS_OBSERVABILITY__TRUST_INCOMING_TRACE_CONTEXT=true` enables continuation.
* **Errors by type only.** Spans record `error.type` and an error status, never exception
  messages or stack traces (they can contain user input).
* **Every process is scrapeable.** Most of the interesting numbers (jobs, tokens, cost, agent
  runs, fetches, queue depth) are produced by workers and the scheduler. They now serve
  `/metrics` from a small embedded Starlette app on uvicorn - no hand-written HTTP parsing - with
  the same bearer token as the API and bound to `127.0.0.1` unless configured.
* **Configuration as code, checked by tests.** The dashboard is generated by a script; tests fail
  when any alert or panel references a metric the code does not export, when an alert has no
  runbook section, when a histogram bucket selector is written in a form that never matches
  (`le="0"` instead of `le="0.0"`), or when the committed dashboard is stale.

## 4. Security
| Risk | Control |
|---|---|
| Telemetry leaks personal data, prompts, documents or credentials | attribute allow-list; route templates not paths; host not URL; SQL parameterised and redacted; errors by type; collector deletes forbidden keys again (defence in depth) |
| Trace headers leak to third-party websites | no HTTP-client auto-instrumentation; a test asserts the fake internet never received `traceparent` |
| Trace injection by clients | incoming context ignored unless trusted |
| Telemetry endpoint downgrade or redirection | production requires an https collector (or explicit plaintext acceptance); the exporter ignores proxy variables |
| Metrics scraped by anyone | bearer token on every `/metrics` (required in production); worker endpoint bound to localhost by default |
| Unbounded label cardinality (cost, privacy) | labels are fixed vocabularies; ids live in spans, never in metric labels |

## 6. Code worth reading
* `instrument_database` - SQLAlchemy cursor events give statement spans and the latency
  histogram from one place, without wrapping every query.
* `TracingMiddleware` - names the span after routing (the template is only known then).
* `AgentRuntime._call_tool` - the tool name in the span comes from the catalogue, never from
  model output directly.
* `tests/integration/test_observability.py` - follows one research job through every layer.

## 7. Tests
* End to end: one trace from the HTTP request to the job (via `jobs.trace_parent`), every stage,
  the planner and analyst runs, model calls, egress fetches and database statements; no span
  attribute contains the objective, an e-mail address, a token, a page path or page text; no
  `traceparent` header reaches the (fake) internet.
* Incoming context ignored by default, continued when trusted.
* The `jobs.trace_parent` CHECK rejects anything but a traceparent.
* Units: propagation round trip, invalid headers, errors recorded by type only, expected
  exceptions, attribute coercion, back-dated spans, bounded operation labels, log correlation,
  provider idempotency, production guards, the token-protected worker endpoint.
* Assets: alert completeness and runbooks, metric names, bucket selectors, dashboard freshness,
  collector pipeline, localhost-only and digest-pinned local stack, middleware order.

## 8. Common mistakes avoided
* Auto-instrumenting the HTTP client that fetches untrusted websites.
* Leaving framework-native telemetry on without reading what it exports.
* Recording `str(exception)` on spans.
* Full URLs (with ids and query strings) as span names or metric labels.
* Metrics that exist only in the API process; alerts on metrics nobody records.
* `le="0"` in a PromQL selector when the client renders `le="0.0"`.

## 9. Scalability
Spans are batched off the request path; head sampling (`OTEL_SAMPLE_RATIO`, default 10%) bounds
volume and child spans follow their parent's decision so traces are never partial. The collector
can add tail sampling (keep every error trace) without changing the application. Prometheus
scrapes each replica; one process per container keeps each registry consistent.

## 11. Acceptance criteria
* One trace links API request, job, stages, agents, model and tool calls and database
  statements; logs carry its `trace_id`.
* No span attribute carries sensitive values; no trace header leaves the platform.
* API, worker and scheduler metrics are scrapeable with a token; every metric is recorded.
* Alert rules and the dashboard reference only exported metrics; every alert has a runbook.
* `pytest`, `ruff`, `mypy --strict`, `lint-imports`, `bandit` green; migration 0013 round-trips.
